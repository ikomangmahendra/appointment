# Adding a Patient to a User's account never exposes a live Patient search

A User books not just for themself but for people they manage — a child, a parent, a coworker. Adding any of these people always looks the same to the User: enter that person's details as if creating a brand-new Patient. There is no search or lookup surface over the full Patient database exposed to a User doing this. Patient Matching (ADR 0004, ADR 0019) already exists to compare Patient records for exactly this kind of similarity, but surfacing its results directly to a User attempting to add someone would leak whether a stranger is a patient at this clinic at all, and would let a User attach themself to — and see the medical history of — a Patient they have no real relationship with, just by knowing a name and phone number.

Instead, when the entered details strongly match an existing Patient (the same 2-of-3 fuzzy threshold, or an exact NIK match, from ADR 0004/0019), the system sends an OTP to that Patient's phone before completing the link, rather than disclosing anything about the match to the User doing the adding. If the OTP isn't confirmed, a new, separate Patient record is created instead, and the potential duplicate falls into the existing Duplicate Candidate queue for staff review — the same outcome a match through any other channel would produce. A false-positive fuzzy match under this rule just costs an unrelated phone number a confusing, ignorable text; nothing links without that phone's own confirmation.

A confirmed link is additive, not exclusive: a Patient can end up managed by more than one User (e.g. both of a child's parents) without any of them losing access.
