# User accounts are Platform-wide, with one phone number unique to each

A User account isn't scoped to a single Klinik — the same login works at any Klinik's booking page, and a User's managed Patients carry over across every Klinik they've booked at. A phone number may be shared across several Patient records (family members routinely share one phone), but is unique to exactly one User account Platform-wide: it's the field a User's identity is OTP-verified against, so a second signup or login attempt with an already-claimed phone resolves into the existing account instead of creating a duplicate.

This was ambiguous going in: ADR 0001's shared-schema multi-tenancy scopes every tenant-owned table by `clinic_id`, which could have implied User is tenant data too, requiring a separate account per Klinik. But Patient is already described as identified "across the Platform" by phone number, and ADR 0017 auto-links a User's existing history by phone match — both of which only make sense, and only deliver real value, if identity is shared Platform-wide rather than siloed per Klinik. `clinic_id` scoping is about which Klinik owns a given piece of operational data (its own Dokter, Jadwal, Layanan, Appointments); it was never meant to silo who a person *is*, which is exactly why Patient Matching and dedup (ADR 0004/0019) exist as cross-record concerns in the first place.
